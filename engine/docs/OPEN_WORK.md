### B. ✅ 已修：`CHANGELOG.md` 那句"关停时强制存档一次"（原文保留，更正如下）

**当时的判断是对的，而且现在修掉了。** 原文（保留以便看出当时看到了什么）：

> 它说"关停时经 `ApplicationStopping` 强制存档一次"。实测**没有发生**：
> `StopAsync` 在排入存盘任务**之前**就 `_stopping.Cancel()`，ticker 循环直接退出、任务从未排空。
> 证据：对照宿主日志说 `Application is shutting down…`，而存档槽没被重写。
>
> **建议**：先**改文档说真话**（"关停不保证存档；请用「存档」按钮"），把 bug 单独记一条。

**实际做的**：没采纳"只改文档"那条建议——`Program.cs` 里那条注释与 1.2.0 的条目都把
"优雅关停存一次档"当成**预期行为**，所以按预期行为修，而不是按现状改文档。
修法：`StopAsync` 先排存盘任务、**等它自己的回执**（不绑 `_stopping`）再取消循环；

### K. ✅ **已实现（1.6.0）**：落定判据从"看过"收紧成"**答完**"（同一条性质的第二次扩大移除）

> **状态**：已实现并跑过 `-Strict`（**469/469**，两个 sln 0 警告）。
> 版本 `1.5.0 → 1.6.0`（minor + 快照再生成），完整条目见 [CHANGELOG](../../CHANGELOG.md) 的

> 还会让"从不作答"变成一条**永远没有收场**的路——不写清楚，下一个人会把它当成缺口顺手改回去。

#### K.1 改了什么

- `EndingSystem.Check` 的推迟判据从
  `待答 && 那批里至少一条没被展示过`（1.5.0）
  换成 **`还有答得上的待答表态`**（1.6.0，`ChoiceSystem.AnswerablePendingCount`）。
  玩家把最后一条答掉之后，结局在下一拍落定。
- **为什么"看过"不够**：它只证明面板画出来了。玩家完全可能正读着题、或者把 sheet 收起来
  打算"待会儿再说"——而结局只有一次，落定就不可逆。**"答完"是玩家自己说"这一项我处理完了"。**

#### K.2 必须写下来的代价（这次比 1.5.0 更宽）

**从不作答的玩家永远拿不到结局。** 1.5.0 起"不会永远悬着"这条性质就已经被移除（那会儿是
"没看到表态面板"），K 把覆盖面扩大到"**没答**"——哪怕玩家把面板看得一清二楚，只要不点，
结局就不来。这是**有意**的，不是漏了兜底。

守它的那条用例三代都是**重写**、从不删除，名字全可 grep：

| 版本 | 用例名 | 守的性质 |
|---|---|---|
| 1.1.0 | `GraceExpiresSoAnUnansweredChoiceCannotStallTheEndingForever` | 宽限一到就照常落定 |
| 1.5.0 | `NotShownChoicesStallTheEndingForeverAndThatIsDeliberate` | 没看过 ⇒ 不落定 |
| 1.6.0 | `ShownButUnansweredChoicesStallTheEndingForeverAndThatIsDeliberate` | **看过也一样** ⇒ 答完才落定 |

#### K.3 风险：一条"答不上"的待答表态会不会把这一局永久卡死？

**这是改之前必须先查清的事**，因为"待答 + 答不上"在新判据下就是死锁。查的结果分两半：

**① 跨层 / 转生 / 读档都不会让一条已经挂上的表态变成答不上（所以新判据不会因此卡死）。**
证据是**三条代码路径 + 两个用例**，不是从 UI 文案推的：

- `PrestigeSystem.ResetRun`（`engine/core/Simulation/PrestigeSystem.cs:141`，被
  `EraSystem.Advance:129` 与 `PrestigeSystem.Ascend:107` 同时调用）清的是
  `Cookies` / `CookiesEarnedThisRun` / `BuildingCounts` / `Buffs` / `GoldenCookies` /
  非永久升级——**一个字都没碰 `PendingChoices`**（它连 `ChoiceAnswers` 都留着，注释里写着
  "跨舍命与转生保留"）。
- `ChoiceSystem.Answer`（`engine/core/Simulation/ChoiceSystem.cs:74`）的三条前置条件只有：
  选择存在、**在待答队列里**、尚未作答。**没有 `EraId` 复查**——`EraId` 只在
  `ChoiceSystem.Check`（触发）那一步当硬门。
- `GameViewFactory.BuildPendingChoices`（`engine/core/Views/GameViewFactory.cs:253`）
  照着 `State.PendingChoices` **全量**建视图，不看当前层；两个宿主都直接用它
  （终端 `GameSession._choiceCache`、Web 的 `state.pendingChoices`）。
- **实测（临时探针，用完已删）**：进第 2 层触发表态 → 舍命到第 3 层 →
  `PendingChoices = [c]`（还在）→ `AnswerChoice("c","a") = True`（答得上）。
  经典转生同理。**用例**：
  `AdvancingTheEraKeepsPendingChoicesAnswerableSoTheNewRuleCannotHang`、
  `PrestigeKeepsPendingChoicesAnswerable`。
- UI 上那句「舍命之后就遇不到了」（`TerminalUi.BuildChoiceTitle`）说的是**触发**：
  `EraId` 是硬门，**没触发**的表态过了那层就再也不会出现；**已经挂在队列里的**不受影响。
  两句不能混为一谈——这正是"不许从 UI 文案推机制"的一个实例。

**② 但"答不上"确实存在两种形态，都只在读档时出现，新判据必须显式放过它们。**

- **内容里已经没有这条表态了**（换内容包，或包改版时重命名/删掉了选择 id）：
  `SaveData.PendingChoices` 只存 id，`SaveSerializer.Apply:129` 原样灌进状态、**不做存在性过滤**；
  于是 `ChoiceSystem.Answer:77` 在 `Content.ChoiceById` 里找不到它 → 返回 `false`，
  而 `BuildPendingChoices` 的 `FindChoice` 也返回 `null` → 它**画不出来、也点不动**。
- **同一个 id 既在已答表里、又挂在待答队列里**（手改的存档、或有缺陷的迁移）：
  `Answer:80` 对"已经答过"直接返回 `false`。

**处置（写进代码的就是这两条）**：

1. 判据只数**答得上**的（存在 && 未答过）——上面两种**不拦结局**。
2. 不拦这件事**必须说出来**：结局就绪时引擎会发一条 Warning 点名有几项答不上
   （"沉默地忽略一批玩家看得见的待答项"正是本项目最反对的失败形态）。
3. 存档里的待答清单**不被改写**（它是诊断信息，判定不该顺手动它）。
4. **用例**：`UnanswerablePendingChoicesDoNotStallTheRunAndTheEngineSaysSo`
   （两种形态各造一份，断言结局照常落定 + 那条警告确实存在 + 清单原样）。

#### K.4 `GameEngine.MarkPendingChoicesShown()` 的处置：**留，但不再是判据**
