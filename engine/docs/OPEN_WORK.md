同一句话，而"两边只差一个字段"正是这次缺陷的形态；③ 报告 §6 的 B（单独常显一行）在 `owned == 0`

**`owned == 0` 时卡片上写什么**：**什么都不写**（那一行整行不出现，与 §19 的「不写『已有 0』」

### 0.15.2 S13：两份实现合成一份，默认启动器现在真的写 `artifacts/latency.txt`

**判定：终端那份是"没写完"，不是"刻意不落盘"。** 三条证据（同一段也写进了合并后那份
类的注释里）：

1. **它自己的注释否证了它自己的行为**：那份 90 行的文件写着"埋点如果在某一条路径上
   不生效，它就会安安静静地什么都不产出，而那正是『沉默失败』最典型的形态"，
   而 `Answered` 的文档写着"宿主据此写日志"——宿主（`GameSession.cs:89`）只把那一行
   写进**游戏内日志面板**，没有任何地方接上文件。它就是那个形态。
2. **历史**：`dbe3183`（Web 那份的来源）标题写"Web 宿主此前没有"，正文把它称作
   "终端宿主那份**参照**"，并列出 Web 比它严的两处；从头到尾**没有一句**
   "终端不落盘是设计"。终端那份在 `cfc238c` / `80e6f59` 里被改过两次，两次都只改
   宽限语义，没有一次提到落盘。
3. **仓库的写作习惯**：凡是有意为之都会写下"刻意"二字（`dnet.ps1` 刻意不用
   `param()`、`RepositoryPaths` 刻意不写死往上几层、旧 `web-smoke` 刻意不进
   `build.ps1`、`Demo.Cli` 刻意不硬编码包清单……）。那份文件里**一个"刻意"都没有**。

**改法：合成一份（`STRUCTURE_OPTIMIZATION` §S13 的形态②），而不是给终端再抄一遍。**

| 文件 | 变化 |
|---|---|
| `games/hosts/Shared/ChoiceLatencyLog.cs` | 新增：`LatencySample` / `LatencyLogFormat` / `LatencyLogFile` / `ChoiceLatencyLog`（命名空间 `NekoClicker.Hosts`），内容取自 Web 那份（446 行） |

**谁写、默认写哪儿**（这一条是本轮唯一的设计决定）：

- 交互模式（`start.cmd` 的默认模式）＝**真人在玩** → 默认写仓库根的
  `artifacts/latency.txt`，与 Web 宿主**同一个文件**（判据同为 `RepositoryPaths.Find()`）。
- `--simulate` / `--frame` ＝**机器人在作答** → **默认不写**；要写必须显式
  `--latency-log`。混进去就等于把"这个文件里只会有真人的数据行"这句承诺作废。

### 量出来的四条（这是"为什么是这一条、为什么只有一条"的全部依据）

1. **点击本来就跟 cps 同步涨，不存在"后期点了没用"。**
   `ProductionCalculator.cs:120` 是 `clickBase = ClickBasePower + 总cps × ClickCpsRatio`，
   再乘 `(1+Σ百分比) × Π乘法`——**每一个点击倍率都在乘"cps 那一项"**。
   所以末局的 `click/cps` 恒等于 `ClickCpsRatio × Π点击倍率`：实测 **0.02 ~ 1.20**
   （即"点一下 = 0.02~1.2 秒的全速产量"；按人手 5 次/秒算是 cps 的 10%~600%）。
   `ClickCpsRatio` 是**包级**参数（0.005 实验室 / 0.01 五个包 / 0.015 咖啡馆与赛博），
   而且**不是**修饰符目标——想把"点击占 cps 的比例"本身做成升级，那才需要动 `engine/core`。
   这一轮**不做**那件事（它是 D11 那一类"要人先拍口径"的改动）。
2. **63 条点击升级里，0 条用 `Scaling`。** 全部是 `ClickFlat` / `ClickPercent` / `ClickMultiplier`
   三种固定写法（这三个 helper 连 `Scaling` 参数都没有，`Modifier.cs:194-204`）。
   其余每一条进阶轴都有成长线（建筑档按数量、牛奶线按成就、联动线按建筑），**只有点击没有**。
3. **点击线从不与"你养了什么"发生关系。** 63 条的门槛全是 `ClicksAtLeast(10/100/200/500/…5000)`
   加"上一档已购"，`ScalingSource.TotalBuildings` 在整个内容层**零使用**（`grep` 命中 0，
   直到这一轮）。所以"点击 ↔ 帝国"这座桥此前不存在。
4. **机器人的节奏对点击收益极度敏感，所以"加多少"只能实测。**
   消融实验（把点击赚到的饼干当场扣掉、点击数照记，因此解锁路径不变）：
   **9 个纪元包没有一个能在 30 游戏小时里走到结局**（最快那个从 1.36 小时变成 >30 小时）。
   直接读出来的"点击收入占比 59%~99%"是**步长产物**（机器人在 `Era>=5` 用 0.25 秒步、
   每步 8 次点击 = **32 次/模拟秒**），不能当玩家的数用；但消融实验作为一个**上界**是有效的：
   **任何点击 buff 都动得了这条机器人的曲线，所以幅度必须小、而且必须报实测。**

   夹具里有而真快照里没有、或形状不同，都点名到**具体路径**。
   同一节还会把**真快照**推过整个 `render()`，并断言**晚段**才该出现的效果
   （四个档位按钮 + 高亮的是 `modeName` 那一个 / 图鉴 / 成就 / 日志 / 建筑 / 离线那张的可见性）
   ——"render 在中段抛异常"这一类故障从此不可能绿。

**判别力（三处故障注入，都是具体的红）**：

| 注入 | 结果 |
|---|---|
| `renderBatch` 写回 `(state.mode ?? "").toLowerCase()`（当年的原样） | 现在**夹具就是真形状**，于是 §3 当场炸：`TypeError: (state.mode ?? "").toLowerCase is not a function at renderBatch`——**整套用例不再可能绿着掩盖它** |
| 夹具写回 `mode: "buy10"`（并去掉 `modeName`） | `夹具里前端会用到的每个路径，形状都与真宿主快照一致 — 夹具与真快照对不上 1 处：· mode：夹具是 string，线上是 number（"buy10" vs 0）` |
| 把**真快照**的 `mode` 改成字符串（模拟"改了老字段形状"那条我没走的路） | `… · mode：夹具是 number，线上是 string（0 vs "buy1"）`——守卫**双向**都响 |
