## 1. 问题

一句话：**现在给 Web 界面加任何东西，都必须改 `app.js` / `index.html`，也就是改框架自己。**

这跟本项目对内容包的主张是**反的**。`engine/docs/ARCHITECTURE.md:277` 把"核心不认识内容"
写成了可执行不变量（`ArchitectureTests` 扫核心程序集：不引用任何 `NekoClicker.Content.*`、
字面量里不出现内容 id），`engine/docs/CONTENT_AUTHORING.md` 全篇的门槛都是"新增一个内容包
**零核心代码**"。可是这个主张只覆盖到 **`.cs` 与 `text.json`**：

| 这一层 | 新增内容要不要改框架代码 |
|---|---|
| 数值 / 条件 / 模块 | 不要（`ARCHITECTURE.md:247` 的"扩展点"表） |
| 面向玩家的**文案** | 不要（十一类全部在 `text.json` 里，`CONTENT_AUTHORING.md:563`~`:774`） |
| **界面本身**（多一个面板、多一个详情视图、多一处动作） | **要**——写死在 `index.html` / `app.js` 里 |

最后一行就是这次的缺口。**十一类文案全在文件里了，但"这些字画在哪"仍然是框架的私事。**

题目这句话的出处也印证了这一点：`STATUS.md:209` 一类的记录里，
每一个界面能力都是"框架侧交付"（「永久线面板」`4365e98`、「日志面板」`602b5c8`、
「离线弹窗」`40d3501`），**没有一条是内容包能自己加的**。

## 2. "这一侧"到底指什么：三种读法，以及证据

题目原文是"把这一侧写成可拓展的外部接口"。这一侧**可以是**三样东西，证据各不相同：

### 读法①（采纳为主）：Web **界面**的扩展面

- **支持证据**：近期的提交全在 `games/hosts/Web/wwwroot/`（§0 表）；
  `MERGE_WEB_FRONTEND_PLAN.md` 把 Web 前端称为"Web 前端可玩闭环"；
  `FRONTEND_CHECKS.md:1`~`:6` 专门为这一层立了一条纪律（"任何 `wwwroot/*` 的改动
  必须附页面真跑过的证据"）。**这一侧有自己的失败史、自己的检查、自己的文档**——
  说明它已经是一个"层"，只是还没有自己的**入口**。
- **不支持的证据（弱点）**：仓库里**没有**任何一处写过"Web 需要插件机制"。
  这是**推断**，不是记录的意图。
- 结论：**这是最贴合"最近几次改动都在这一侧"这条线索的读法，本文按它展开。**

### 读法②（同样站得住）：**创作**侧的对外契约——`text.json` 的版本化

- **支持证据**：这条线索是**写在文档里的**，不是推断出来的。
  `TEXT_AS_DATA_PLAN.md` 把"可读文件"当成对**内容作者**的承诺；
  `CONTENT_AUTHORING.md:613` 起明确"内容包目录里有 `text.json` 就自动生效"；
  十一个分区（`ContentText.cs:24`~`:27`）已经是一份**事实上的 schema**；
  守卫 `ContentTextFileTests` 有 **31** 条（`TEXT_AS_DATA_PLAN.md:588`）。
- **它现在缺什么**：这份 schema **没有版本号**。`ContentText.Load` 不读任何 `version` 字段，
  加一个分区/改一个字段名对老文件是什么后果，**没有一处写着**。
  一个新内容包作者（或第三方）今天拿到的是一份"能跑但无承诺"的格式。
- 结论：**如果"外部接口"指的是"让别人能稳定地写内容"，那答案是它，而不是 UI。**
  它与读法①**不冲突**，是**另一条轴**（见 §11 的 D1）。

### 读法③（可能性较低，但不能排除）：给**别的宿主**的接口

- `ARCHITECTURE.md:263` 最后一行就写着"换前端：只依赖 `GameSnapshot` 与引擎的公开命令方法"。
  按这条，`GameSnapshot` **就是**已有的外部接口，`VERSIONING.md` 全篇在承诺它。
- 那么"写成可扩展的"可能指**把宿主接口正式化**：新宿主（TUI / Godot / 命令行机器人的）
  接入清单、`GameSnapshot` 的版本承诺、以及"宿主能做到什么"的成文边界。
- **支持证据**：`VERSIONING.md:108`~`:112` 说"内容包是用公开 API 写出来的东西"，
  `ARCHITECTURE.md:249`~`:263` 已经有 12 行"扩展点"表。
- **弱点**：没有具体缺口被记录（不像①有"界面写死"、②有"schema 无版本"）。
  这条更像"文档补全"，不像"接口设计"。
- **注意**：读法①**必然包含**读法③的一半——一个真正的外部 UI 接口，本身就是给第三方宿主的。

> **本文的取舍**：主体按**读法①**设计（它最贴合"最近改动都在这一侧"），
> 但 §3 的**方案 D0/D1/A/B/C 五选**与 §11 的 **D1**（读法选择）把读法②③当成**并行的选项**摆出来，
> 不替人拍板。**谁也没权利用一个推断的读法覆盖一条写着的线索。**
>
> 注意本文有两处同名的标签，**不是笔误**：
> §2 的**读法①/②/③**是"这句话指什么"，§3 的**方案 D0/D1/A/B/C**是"做哪一档"，
> §11 的 **D1~D9**是"要人拍板的决定"——其中 §11 的 D1 恰好在问"选哪个读法"。

## 3. "扩展"在这里具体是什么：五档，从"什么都不做"到"提升成引擎概念"

### 方案 D0：什么都不做（对照项）

把界面继续当框架私事，每个包想要什么就在 `app.js` 里长一个 `if`。
代价见 §8 的"不做的理由"——**这条真的可以选**，它现在是能跑的。

### 方案 D1（最小）：**只把已有的建筑描述画出来**

不改任何声明面：`BuildingView.Description` 已经在快照里（`Views.cs:18`、`GameViewFactory.cs:61`），
在建筑卡片上加一个可展开的详情区即可。

- **好处**：**不新增任何契约、不升版本、不碰引擎**。
- **代价**：它只解决"建筑有一句描述"，**不解决"包能自己加东西"**。
  第二个包想要第二种面板时，还是回到 `app.js`。
- **⚠️ 这一条正在被另一轮改动实现**（§0.2，工作区未提交）。它把 `renderBuildings` 拆成
  `createBuildingRow` / `updateBuildingRow` + 一个 `[📖]` 展开按钮 + `.story` 区域，
  文本来自 `description`，冒烟用例 67 → **82**。**本文对它的描述以那轮改动为准，不重复设计。**

> **D1 是①的真实第一步，也是①的诚实上限。** 如果人只想要"建筑能讲故事"，
> 那么 D1 落地这件事就**结束**了，本文后面全部内容都不必做——
> 而**那轮改动正在这么做**，这本身就是"最小有用面"的最好证据：
> 一个真实的界面需求，**没有碰引擎、没有新增契约**就做完了。

> **D1 做完之后，A 的动机只剩下一条**：那轮改动里，故事文本来自
> `text.json` 的 `buildings.<id>.description`（每座建筑**一句话**），
> 而"这一座建筑的一段故事"（多段、有标题、甚至可以带上跨建筑的页）**没有任何地方可写**。
> **A 只有在包真的需要"写不止一句话"时才值得**——见 §10 的对照项。

### 方案 A（推荐，①的主线）：**宿主侧的声明式界面扩展**

内容包**声明**界面块，宿主把它变成快照里的一个**新顶层字段**，前端按**白名单原语**渲染。
内容不提供代码，只提供数据。

### 方案 B（①的最强形态）：**引擎侧的通用视图扩展**

`engine/core` 新增 `UiSectionView` 之类的公开类型，`GameSnapshot` 带上它，
把"界面块"提升成**引擎级**概念。

- **好处**：终端宿主（`games/hosts/Demo.Cli`）**同样**能渲染它，"一次声明两个前端都吃"。
- **代价**：**引擎开始知道"界面长什么样"**。这与 `ARCHITECTURE.md:49` 的单向依赖
  （`Views` → `GameEngine` → …）以及"引擎不认识 HTML"的既有立场直接冲突；
  而且是公开 API 变更（`VERSIONING.md:69`：公开 API 只增不改 = minor）。
  本章**不推荐**它作为第一步，理由见 §7 的备选讨论。

### 方案 C（读法②的正解）：**`text.json` 的版本化外部契约**

给 `text.json` 加 `version`、把十一个分区冻结成有版本号的外部 schema、
补一份"给第三方内容作者"的独立文档、并在 `ContentText.Load` 里对未知版本**当场抛**。

- 它与 A/B **不冲突**：A 管"界面块从哪来"，C 管"文字文件对谁有承诺"。
- 它的**独立价值**在 §2②：一个第三方内容作者今天拿到的 schema 无版本。

**本文的推荐组合是 `D1 + A + C`**（D1 已在另一轮改动里落地中，A 待需求出现，C 可以并行），
**B 留作后备**。下面按 A 展开，因为它是"可扩展接口"这句话的实质。

## 4. 方案 A 的两个用例（做成什么样）

### 用例一：一个包自己声明一页"名册"

`engine/content/NineLives/ui.json`（示例，**尚未存在**）：

```jsonc
{
  "schema": 1,
  "panels": [
    {
      "id": "roster",
      "kind": "panel",              // 白名单原语之一
      "title": "九命名册",
      "order": 30,                  // 页签次序；框架既有面板用 10/20/…，扩展从 30 起
      "blocks": [
        { "kind": "heading",  "text": "已经走过的命" },
        { "kind": "text",     "text": "每一命都留下一个名字。" },
        { "kind": "list",     "source": "counters", "id": "lives_lived" },
        { "kind": "text",     "text": "当前有 {amount:prestigeChips} 枚徽章。" }
      ]
    }
  ]
}
```

前端把它渲染成**第四类页签**（`#tabs` 里动态追加一个按钮 + `.panels` 里一个
`[data-panel="ui:roster"]`）。**页签的壳是框架的，内容是包的**——这正是"可扩展"的意思：
包能决定"有什么"，决定不了"用什么 HTML"。

### 用例二（直接动机）：建筑的**多段**叙事

工作区里那轮改动（§0.2）已经把故事框做出来了，但它读的是
`text.json` 的 `buildings.<id>.description`——**每座建筑一句话**，
而且那句话在界面上还有另一个身份（未解锁时它是"说明"）。所以**仍然没有地方**放
"这一座建筑的一段故事"（多段、带标题、可以只在展开时才讲）。用同一个机制表达：
**按 id 引用**，不做模板引擎。

`engine/content/Lab/ui.json`：

```jsonc
{
  "schema": 1,
  "buildingSections": {
    "incubator": { "title": "培养舱",
                   "text": "它记得上一个住客的温度。\n\n记录本上写着：第 41 次尝试，仍未见心跳。" },
    "centrifuge": { "title": "离心机", "text": "转速表早就坏了，没人敢修。" }
  }
}
```

- 宿主在生成快照时把它**按建筑 id 拼进 `BuildingView`**（新字段 `UiSectionId`，见 §6），
  前端在建筑卡片展开时按 id 取那一块。
- **这一条与用例一的差别**：用例一是"新面板"，用例二是"已有面板里多一块"。
  两者共用一个声明文件、一套校验、一个渲染器——**这就是"最小的有用面"**。

## 5. 声明住在哪：**内容包目录下的新文件 `ui.json`**，而不是 `text.json`

### 定论：**独立文件**（`engine/content/<包名>/ui.json`）

| 候选 | 判据 | 结论 |
|---|---|---|
| **扩 `text.json` 的新分区**（如 `ui`） | 与 `CONTENT_AUTHORING.md:661` 起那条**负载性**约束直接冲突：`EnsureNoOrphans` 会遍历**整份文件的所有类别**，所以**一个包只能有一个 `ContentText` 实例**；而 `ui.json` 的读者是**宿主**，不是内容包代码 | **不选**（除非同时放松孤儿检查，那会削弱 §7 的一条守卫，见 §11 的 D2） |
| **新的 C# 接口**（内容包实现 `IWebPanelProvider`） | 违反 A3 的一半：那要求每个包写 C# 扩展代码、并引用宿主程序集；而 `VERSIONING.md:33` 说内容包之间互不引用是硬规矩，包引用宿主是更坏的方向 | **不选** |
| **包目录下的新文件 `ui.json`** | 与 `text.json` 完全同构：`Directory.Build.props:81`~`:86` 那条 `ItemGroup` 已经是"包目录里有这个文件就复制到 `content/<包名>/`"——**加第二条 ItemGroup 即可**，机制现成、发布产物也带上、新包放个文件就生效 | **选它** |

**为什么不叫 `ui.json` 之外的别的名字**：`web-ui.json` 更能说明"这是 Web 宿主的"，但它会
暗示终端宿主将来不能读；而这个文件的**内容本身与宿主无关**（它是"界面块"，
不是 HTML）。名字保持 `ui.json`，把"谁能读它"写进文件头注释与 §10 的 D3。

**包的代码要不要知道 `ui.json`？** **不要。** 内容包的 `Build()` 一行都不改——
与 `text.json` 的区别正在这里：`text.json` 是**包自己**读的（`ContentText.Load`），
`ui.json` 是**宿主**读的（它已经有包 id 与 `GameContent`，见 §6）。
于是"有 `ui.json` 的新包零 C# 代码"这条成立，A3 不被侵蚀。

> （见 §11 的 D1）。

### 增量协议：**不需要为它加任何特例**（这是关键结论）

`SnapshotProtocol.Diff`（`SnapshotProtocol.cs:150`~`169`）是按**顶层字段**比的：
新增一个顶层 `ui` 字段之后

- **`ui` 没变** → 增量帧里**一个字节都不带它**（`before`/`after` 该字段文本相同即跳过，第 159 行）；
- **`ui` 变了** → 带**整个 `ui`**，但**不带** `buildings` / `upgrades` / `codex`。
  也就是**负载是按扩展声明的粒度走的，不是按帧走的**。

而且 §6 的声明是**每包静态**的：它**从构造到关服都不变**，于是**永远不会进增量帧**，
只在第一帧全量与每 120 个序号的全量对账（`GameHost.cs:63` 的 `FullResyncEvery`，
`GameHost.cs:60` 的 4 Hz）里出现。**"每帧背所有扩展的负载"这件事在结构上不会发生**——
这正是题目担心的那一条，而答案是：**协议已经保证了它，只要声明是静态的、按需出现的。**

**唯一需要防的是"动态、每帧都变的大块扩展"**（例如一个每秒刷新的自绘柱状图）。
防线是一条**已有的**用例：`engine/tests/WebSnapshotProtocolTests.cs:368` 的
`IdleDelta_StaysSmallInBytes_EvenWhileProgressDrifts`，第 394~395 行的判据是

```csharp
deltaBytes * 20 < fullBytes      // 增量必须小于全量的 5%
```

**这条用例会替我们抓住"某个扩展把增量帧撑起来"的每一种写法**，不需要新增纪律。

## 7. 前端被允许做什么：安全子集与明确禁止

**原则：内容只声明，框架才执行。**（题目原话："anything that runs must be code that ships
with the framework/host; content may only *declare*."）

### 允许（v1 白名单，**封闭集合**）

| 原语 | 形状 | 渲染成 |
|---|---|---|
| `heading` | `{ text }` | `<h3>` |
| `text` | `{ text }` | `<p>`，**只走 `textContent`** |
| `list` | `{ source, id }` | 读快照里**已存在**的列表（如 `buildings` / `codex.storylines` / `achievements`）画只读行 |
| `stat` | `{ source, label }` | 快照里**已有**的一个数值字段 + 标签（`source` 是**字段白名单**） |
| `buildingSection` | `{ title, text }`（按建筑 id） | 建筑卡片的展开区（`<details>`） |
| `counter` | `{ id, label }` | `state.counters[id]`，内容包已通过 `AddCounterName` 登记的计数器 |
| `order` / `id` / `title` | 元数据 | 页签次序、DOM id、标题 |

### 允许的**取值**（这是"声明"里唯一的运算）

`text` 里可以有占位符，**替换发生在宿主的校验/折算阶段**（不是前端，也不是内容）：

| 占位符 | 取自 | 失败行为 |
|---|---|---|
| `{amount:<快照字段>}` | 数字字段，按 `NumFormat` 口径 | **未知字段名 → 当场抛**，不是原样显示 `{amount:xxx}` |
| `{percent:<快照字段>}` | 同上，百分号化 | 同上 |
| `{duration:<快照字段>}` | 同上，`NumFormat.Duration` | 同上 |
| `{text:<快照字段>}` | 字符串字段 | 同上 |

> 这条是**刻意设了上限**的：`TEXT_AS_DATA_PLAN.md:531`~`:537` 已经就"要不要发明模板引擎"
> 做过一次判断（结论：**不发明**，按 id 展开成成品）。这里**只留四个替换标记**，
> 没有表达式、没有条件、没有循环——**它不是模板引擎，是四个格式化函数。**

### 明确禁止（写进文档，也写进守卫）

1. **`eval` / `new Function` / 注入 `<script>` / 任何 `innerHTML`**。
   内容给的字符串**一律**经 `textContent`（仓库既有写法：`app.js:476`、`app.js:481`、
   `app.js:491` 全部是 `textContent`）。**`innerHTML` 只允许赋空串**（既有用法，`app.js:539`、`app.js:564`）。
2. **内容提供回调 / 事件处理器 / URL**。扩展**不能**新增可点击动作，
   不能新增命令类型（宿主的命令白名单 `/api/command` 保持封闭，`Program.cs:213`~`:320`）。
   *理由*：一个内容作者能定义"点这个按钮跑什么"，就是任意代码执行的第一步。
3. **内容提供 CSS / 类名 / 颜色**。样式全部来自 `app.css`。
   *理由*：类名是**框架的内部契约**（`.panel` / `.card` / `.hidden`），
   放开等于让包依赖框架的 DOM 结构，下次重构就静默坏掉。
4. **新面板自己拉数据 / 自己的定时器 / 自己的网络请求**。扩展只能读**同帧快照**里已有的东西。
5. **可见性条件树**（"只在第 3 层显示"）。v1 **不做**——
   一旦有了条件，就要有校验器、单调性讨论、可达性分析，那是 `UnlockCondition` 那一整套的复制品。
   需要条件的内容作者**现在**的写法（`HiddenUntilUnlocked` 一类）已经够用。
   *这是一条**刻意留白**，见 §11 的 D6。*

## 8. 失败模式：每一类都必须**响**

题目原话："malformed extension declaration must produce a clear error, never a silently
missing panel"。逐类：

| 失败 | 谁发现 | 怎么响（消息必须带包名 + 文件路径 + id） |
|---|---|---|
| `ui.json` 不是合法 JSON | **宿主加载时**（`JsonNode.Parse` 的异常**不吞**） | 抛 `InvalidOperationException`，正文含文件绝对路径与解析器原始位置 |
| 缺 `schema` / `schema` 不是 1 | **宿主加载时** | 抛，正文说明"这份声明的版本是 X，本宿主只认 1" |
| 未知 `kind` | **宿主加载时** | 抛，正文**列出白名单全集**（不是"不认识 kind"，而是"不认识 kind「carousel」，这一版只认 heading/text/list/stat/…"） |
| 缺必需字段（`text` 的 `text`、`list` 的 `source`） | **宿主加载时** | 抛，正文点名"panel `roster` 的第 3 个 block" |
| 必需文本为空串 / 全空白 | **宿主加载时** | 抛（照 `CONTENT_AUTHORING.md:759`~`:764` 的判据：**空 ⇒ 界面回退成别的东西**，正是要消灭的静默路径） |
| `id` 重复（同一文件内） | **宿主加载时** | 抛，正文报出两处 id |
| `buildingSection` 引用的建筑 id **不存在** | **视图构建时**（要 `GameContent` 才判得了） | 抛，正文列出该包**全部合法建筑 id** |
| 扩展引用**不存在的实体**（`list.source` 不是快照字段、`stat.source` 不在白名单） | **宿主加载时**（白名单是静态的） | 抛，正文列出白名单 |
| 某座建筑**没有** `buildingSection` | **不响** | 这是**合法**的：不是每座建筑都要有故事（与 `TextOr` 的"可选文本"同性质）。**但守卫要钉住"有几个"**（§9），否则"全都没写"会被读成"都写了" |
| `ui.json` 存在但**一个块都没有** | **宿主加载时** | 抛（空文件 = 作者以为写了什么） |
| 声明的面板**引用了计数器 id 但包没登记** | **视图构建时** | 抛（与 `ARCHITECTURE.md:255` 的"未登记则回退成键本身"相反：**这里不许回退**，理由同上） |

**"响在哪一层"的判断规则**（照抄仓库已有的分工）：

- **只有看 `GameContent` 才判得了的** → **视图构建时**（建筑 id、计数器 id）；
- **看文件自己就判得了的** → **宿主加载时**（结构、白名单、必需字段、重复 id）；
- **"代码与文件同时少一条"这类盲区** → **构建期守卫**（§9 的条数表，
  理由见 `CONTENT_AUTHORING.md:674`：**纯双向比对发现不了两边都少一座**）。

**一次坏的 `ui.json` 会不会拖垮整个包目录？** **不会**，这是刻意的：
`PackageCatalog.ReadTitle`（`PackageCatalog.cs:90`~`:101`）已经确立了"不让一个坏包拖垮整个目录"
的立场。但**"不拖垮目录"不等于"静默"**：错误要进 `/api/packs` 的响应与宿主控制台，
**并且该包在会话创建时如实报错、拒绝开这一局**（不是开一局空白界面）。

## 10. 成本与风险

### 这个方案让以后更难的地方

1. **多了一层要维护的契约**。`ui.json` 一旦发布就**有外部作者**了，
   以后改白名单 = 破坏他们的文件。要按 `VERSIONING.md` 的规矩对待它（`schema` 字段是为此留的）。
2. **前端多了一个"解释器"**。`app.js` 从"画固定的东西"变成"按数据画东西"，
   于是**渲染的正确性不再一眼可见**：以前看代码就知道页面长什么样，
   以后要看**数据**才知道。这是所有声明式 UI 的共同代价。
3. **"包能自己加面板"会把界面拉散**。今天十一个包的界面是**统一**的（这是优点：
   玩家换包不用重学）。放开之后，每个包可以长得不一样。**这条要人明确认可**（D7）。
4. **引擎多一个公开字段**（若走 §6 的"完整版本"）：`GameSnapshot` 的承诺面变大，
   之后每一个 UI 概念都要过一次版本流程。

### 什么都不做的理由（对照项，必须认真摆出来）

- **十一个包里有几个真的需要？** 到本文写作时为止：**没有**一个包有一个自己需要的界面块——
  唯一的候选是"建筑描述"，而它**已经被引擎推过来了**（`Views.cs:18`），
  **不需要任何扩展机制就能画**（D1）——而且**已经有人这么画了**（§0.2，工作区里那轮改动）。
- **D1 的性价比碾压 A**：D1 = 一个展开区 + 一批 DOM 代码，**零契约、零版本、零新守卫**
  （它只新增冒烟用例）；A = 新文件类型 + 新校验器 + 新白名单 + 新守卫 + 一次 minor
  + schema 版本承诺 + 一份给第三方的文档。**这个对比是实测的，不是估的**：
  §0.2 那四个文件就是 D1 的全部成本。
- **"以后可能要"不是现在做的理由**。本仓库的方法论是"先做一个包试点"
  （`TEXT_AS_DATA_PLAN.md:104`）——而 A 的试点包**目前不存在**：
  没有人真的在等第二个面板。
- **最大的风险是"接口做出来没人用"**，其次是"第一个真用户的需求与设计不符"。
  两者的对策都是同一条：**让 D1 先落地（它正在落地），等第二个真实需求出现，
  再按那个需求来定 A 的形状。**

> **本文的建议（但决定权不在这里）**：
> **D1 已经在另一轮改动里落地（不要重复做），A 的设计照本文写着但先不实现**，
> 等第二个真实需求出现再按它落地。判据是 §4 用例二末尾那条：
> **看内容作者会不会绕过 `description` 去别处塞故事**。
> 如果人认为"外部接口"本身就是交付目标（而不是为了某个具体界面需求），
> 那 A 应该做，**但那时 §11 的 D1~D9 必须逐条定完**——尤其 D3（schema 承诺）与 D4（动作白名单）。

4. **不做通用组件库**（没有 table / chart / input / modal 原语）。这一版只解决
   "一页文字 + 已有列表 + 一条数值"这三种。

10. **不放松任何既有守卫**去换这个特性（尤其 `EnsureNoOrphans`，见 D2）。
