## 一、难度跨度：1.4 ~ 11.8 游戏小时（8.4 倍）

数字来自 `PrestigeTests.EraPacks_PermanentUpgradesAreAffordableWithinOneRun` 每次运行打印的
实测行（机器人跑到结局，不是估计）：

| 包 | 到结局的游戏小时 | 层数 |
|---|---|---|
| #4 文明 | 1.4 | 5 个时代 |
| #10 公司 | 1.9 | 3 轮重组 |
| #6 末世 | 3.0 | 5 次重启 |
| #5 赛博 | 5.3 | 5 层 |
| #3 实验室 | 5.9 | 7 批 |
| #8 梦境 | 6.0 | 5 层梦 |
| #7 神明 | 7.5 | 5 套神话 |
| #9 图书馆 | 11.1 | 5 本书 |
| #2 九命 | 11.8 | 9 层 |

⚠️ **这张表是 2026-10-02 在 `1ac2a9d` 那棵树上量的，其中两行已经不对了**（实验室 5.9 → 今天 4.50、
公司 1.9 → 今天 1.51）。原因**实测**清楚了：差的是"机器人开始答表态"这一件事，**内容没有漂**
——证据与三组对照跑见 **§4.5**；每层各自的时长见 **§4.2**。

**先把话说清楚：这不是"难度"的跨度，而是"内容量"的跨度。** 层数从 3 到 9，
每层各自的时长也不一样，两者相乘就是这 8.4 倍。所以"该不该收敛"取决于一个
**只有你能回答的问题**：你希望一局是多少小时？我能算，但"多久算合适"不是技术问题。

### 选项（按代价从低到高）

- **(a) 不动。** 8.4 倍的跨度本身就是内容差异的体现（九命 9 层 vs 公司 3 轮）。
  代价：玩家看到"这一局要 12 小时"时可能直接不开始。**零工作量。**
- **(b) 只收敛最长的那两个（图书馆 11.1 / 九命 11.8）**，把层内门槛压低。
  代价：要重跑包络测量（`--simulate` 到结局）并重设门槛，且**动的是已发布内容的平衡**，
  会影响老存档的进度观感。中工作量。
- **(c) 给所有包一个统一的"到结局时长目标"，逐个标定。** 代价最高，
  而且会抹掉"不同包规模不同"这个可能是刻意的差异。**我不推荐**，除非你确认要统一。

**我倾向 (a) 或 (b)，而 (a) 其实是更诚实的默认**——因为没有任何证据表明
8.4 倍是错的；它只是"不一样"。要动它，先要有一个目标值。

## 二、套件墙钟：并行之后瓶颈变成了一条用例

实测（`tools/build.ps1 --timing` 与 `--timing --serial`）：

| | 串行 | 并行（16 核） |
|---|---|---|
| 全套墙钟 | 261.1s | **149.7s** |
| `PrestigeTests.EraPacks_...` 单条 | 98.5s | **143.9s** |
| 其余 430 条合计 | ~163s | —— |

**关键发现**：并行把这个套件从 261s 压到 150s，但**最慢那条自己被 CPU 竞争拖慢了**
（98.5 → 143.9s），于是**整个套件的墙钟现在由它一条决定**。再加线程没有用——
瓶颈已经从"CPU 总吞吐"变成"单条最贵的用例"。

那条用例在做什么：把 **9 个包各跑一局到结局**（就是上表那些小时数的来源）。

### 三个杠杆与它们的真实代价

| 杠杆 | 预计 | 代价 / 风险 | 对玩家有好处吗 |
|---|---|---|---|
| **② 让每个固定步更便宜** | **未测** | 低（改的是 `ProductionCalculator` / `ModifierResolver` 这类纯计算） | **有**——真玩时的帧率也吃这条 |
| **① 跨用例共享"跑一局"** | 261 → 约 180s（估） | 中：要统一"什么叫一次自然游玩"，而那会**改变多个守卫重放的轨迹与打印的数字**；这类改动最容易变成"数字变了，但不知道是内容坏了还是机器人换了" | 没有 |
| ③ 再加并发度 | **0** | —— | 没有（已被单条瓶颈限制） |

**我建议先做 ②，而且第一步是"测"不是"改"**：套件里 11 个包总共要快进三千多游戏小时，
成本 = 模拟秒数 × 30Hz × 每步成本。**每步成本目前只是一个从两个数据点推出来的估计
（约 23 µs）**，没有单独测过。测法：用 `--timing` 对比同一份内容在"只推时间"与
"推时间+买卖"两种机器人下的逐条耗时，把每步成本与外围开销（`BuyGreedily` 每次建
整份 `Snapshot`）分开。**分开之后才知道该优化哪一边**——否则很可能花大力气优化了
占小头的那半边。

**①要谨慎**：它的收益（省 80s 左右）不如它的风险大。它属于"动守卫重放内容"的改动，
而这个仓库今天已经因此栽过一次（粗步长让探针量的是步长而不是内容）。

## 四、舍命之后：每一层各用多久，其中多少是在重走（2026-10-03 实测）

> 玩家玩后原话：「玩了一会，感觉舍命之后从头再来的次数太多了」。
> 他玩的是**公司**（3 层）与**末世**（5 层）——两份存档的 mtime 是最近的，见 §4.8。
> 这一节**只做测量与选项**：门槛、倍率、内容、引擎行为**一个都没动**。

### 4.1 怎么量的（复用仓库自己那条机器人，没有新发明）

- 机器人 = `PrestigeTests.EraPacks_PermanentUpgradesAreAffordableWithinOneRun` 的**逐行复制**：
  8 次点击 → `TestGame.BuyGreedily` → 点金猫 → 答掉待答表态 → 能舍命就舍命 → `Simulate(30)`
  （`Era >= 5` 起改 0.25 秒细步），30 游戏小时上限，种子 12345。**§1 那张表的来源就是它。**
- 临时探针（`.tmp/EraProbe`，`.tmp/` 已 gitignore、**不在仓库里**）在同一段循环里加了三处观测：
  ① 订阅 `BuildingPurchasedEvent` / `UpgradePurchasedEvent` / `LoreRevealedEvent`（带"距本层开始多少秒"）；
  ② 每次 `Ascend()` 成功**前后**各记一次状态（进了几座建筑、cps、保留的升级、计数器、可见建筑、
  本层的 `EraGate.Progress`）；③ 每层结束时记录时长与本层累计赚取。
  "重走"的三个指标就是从这三处算出来的（定义见 §4.4）。
- 在**独立的 `git worktree`** 里构建运行：宿主正在 `127.0.0.1:5273` 上服务，主工作区的产物没被碰
  （全程 `git status --porcelain -- engine/content` 为空、`bin/` 里没有新东西）。
- **9 个包各跑一局到结局：一次 105.5 秒**（不是小时）。另有四组对照跑：三组在 §4.5、一组在 §4.6。
  （探针本体与三份分析脚本留在 `.tmp/EraProbe-src/`、`.tmp/analyze*.py`、`.tmp/tune-out/*.json`——
  都在 gitignore 里、随时可删；复跑要把探针放进一个 worktree。）

### 4.3 舍命之后还剩什么（继承 vs 全清）

`PrestigeSystem.ResetRun` 的清空清单是：货币、本轮累计、**建筑**、增益、场上金猫、**非永久升级**；
保留的是成就、累计统计、转生货币、永久升级，以及**计数器**（源码注释写明"刻意不清空"）。
"这一层允许带进来什么"写在**目标层**的 `EraDefinition.InheritBuildingRatio` / `InheritBuildings` 上。

| 末世 | 0.25 / 0.4 / 0.55 / 0.7（第 3、5 层另有白名单） | 15 / 91 / 165 / 183 座 | 44.5 → 1,396,096 | 0 |

- **9 个分层转生包里只有末世真的做了跨层继承**；其余 8 个包的 `InheritBuildingRatio` 全是 0
  （这条已有守卫：`ApocalypseContentTests.InheritBuildingRatio_DefaultsToZero_Elsewhere`）。
  于是"舍命之后从零开始"对 8/9 个包是**字面意义上的**：进层 0 座建筑、cps 0.0。
  连**可见建筑数**都回到了开头（实测进层时 `IsUnlocked` 的建筑数）：
  公司 / 实验室 / 神明 / 文明 / 赛博 / 梦境 **每一层都是 1 座**；
  九命**每一层都是 0 座**（它的解锁门挂在本轮累计上，进层连第 1 座都要重新挣）；
  只有末世与图书馆因为解锁门用历史累计，进层可见 5 → 9 座。
- 跨层保留的是**计数器**（实测进层时：公司士气 4353→1.16e4、末世记忆残片 5580→1.46e5、
  九命信仰 932→8.05e4、实验室伦理 552→2176……）。所以"全新的"只有建筑与升级这条线，
  而它正是购买序列的主体。
- 保留的升级实测是 0：非永久升级一定被清掉，而**机器人按那条守卫的约定根本不买永久线**
  （`PrestigeTests` 的注释："转生升级留给这条断言去算"）。两份真人存档的 `Upgrades` 也都是空的——
  所以"永久线在真人这一局里有没有被买到"是**另一件事，本节没测**。

### 4.6 是"次数"还是"每次都一样"？数出来偏向后者，但有两条边界

**数"次数"**：一局 2~8 次舍命（公司 2 / 末世 4 / 九命 8），而且**第一次舍命只占整局 2%~33%**——
按次数看，"公司只有 2 次"并不算多。

**数"一样"**：8/9 个包舍命后进层 **0 座建筑、cps 0.0**，可见建筑回到 1 座（九命是 0 座）；
第 1 层买过的**每一座**建筑都在之后每一层的最前面以**同一顺序**再买一遍（§4.4 那张表）；
第 2 层起，每层的建筑购买里 **43%~100%** 是"再买一次"（后段层普遍 ≥80%，很多是 100%）；
每层有 **1%~100%** 的时长花在"重挣到上一层那个量"之前、**0%~100%** 花在"第一次买到上一层没有的东西"之前
（很多后段层是**整层都没有新的**）。

**这两件事指向完全不同的修法**，所以我专门测了区分它们的那一档（丢弃式反事实，改完即弃）：
**只动继承比例、层数与门槛一个字不动**——把公司第 2/3 层的 `InheritBuildingRatio` 设成 0.25 / 0.4 之后：

| | 基线（今天） | 反事实（0.25 / 0.4） |
|---|---|---|
| 公司整局 | 1.51h | **1.13h** |
| 第 2 层 | 41.5min | **31.0min** |
| 第 3 层 | 23.0min | **11.0min** |
| 第 2 层"把第 1 层挣过的再挣一遍" | 18:29 | **7:00** |
| 第 2 层第一次买到新东西 | 28:29 | 19:30 |

**两条边界（不解决，"是次数还是一样"就仍有一半没答）**：

1. 上表的时间是**机器人**时间。真人比贪婪机器人慢多少，仓库里**没有数据**
   （`artifacts/latency.txt` 仍然是 0 条 `S` 行）。你那份存档里的 `PlayTimeSeconds` **不能**当注意力时长用：
   宿主按真实时间推进（`MaxCatchUpSeconds = 5` 只截断大跳，进程一直在跑），挂机也在涨——
   证据是公司第 1 层 4.55 引擎小时里 `TotalClicks` 只有 268，末世 32.18 小时里只有 104 次点击。
2. 我量的是"买了什么、什么时候买"，不是"感觉像不像重复"。开场那四座建筑的**操作**是否让人厌烦，只有你能判。

### 4.10 玩家的决定，与 1.9.0 落到了哪一步（2026-10-03）

**原话（逐字）**：

> 「重来两次，但每层 n 个阶段」

也就是说：不是 §4.7 的 (b) 或 (c) 或 (d) 里挑一个，而是**换一条形状**——
**一局只重来两次**，而一局之内的进度靠**一层之内的 n 个阶段**往前推。
这条回答同时定了 §4.9 那个问题的一半：次数要少（≈2 次），而"每次都一样"那半由分段解决。

**1.9.0 只落了这条决定的"分段"那一半，而且只落在一个包上**：

| 决定的一半 | 这一版做了什么 | 依据 |
|---|---|---|
| 一层之内分成 n 段、跨段不清 | **做了**：`EraDefinition.Stages` + 派生 + 两个宿主的显示 + 播报；试点是**公司**（5 / 8 / 8 段） | 公司**本来就只有 3 层 = 2 次重开**，正是"重来两次"那个形状——所以它是零风险的第一个试点 |
| 一局只重来两次 | **没做**：其余 8 个包仍然 4~8 次 | 减层要重切每层门槛，那是**改数值**；而"少掉的那几次舍命值多少"还没有量 |

**为什么先做分段、而不是先减层**（顺序是有理由的，不是随手）：

1. **减层会重切阶段线。** 九命的 9 层折成 3 层，每层的完成门槛必然重定，
   而阶段边界就是挂在那些门槛**之下**的线（`CONTENT_AUTHORING` §11.2.6）——
   先定 n 再减层等于白定一遍。
2. **分段的代价是零，减层的代价不是。** 这一版**一个数值都没改**（阶段是**派生**的：
   它只把内容里**已经存在**的门槛说出来），所以 §1~§3 那些实测表**一格都不用重跑**；
   减层则要重跑 §4.1 那套机器人，还要面对"叙事 / 表态 / 终局判定都挂在层上"（§4.7 (d) 的代价）。
3. **减层需要一个前提值，而它只能量出来**：`ChipsOnAdvance` 是**每一次**舍命注入一笔
   情感能量（`max(0, level - PrestigeLevel) × MetaRewardMultiplier`），
   而永久升级线（1.4.0）就是花它的。一局从 8 次注入压到 2 次，
   **注入密度掉了 4 倍**——如果阶段不接住这部分奖励，形状会"重复少了、但也不再变强"。
   **所以先量**：用 §4.1 那条机器人跑一遍"每段给 X"的丢弃式反事实（改完即弃），
   拿 §4.2 / §4.4 同两张表比，再决定"每段给一次"还是"每层给更多"。
   在那之前给任何数都是拍脑袋。
4. **机制已经先在位了**：`EraSystem.Stage(engine)` 与计数器键 `$era_stage_<纪元 id>` 都是公开的，
   于是**包自己的模块**可以在跨段那一刻用**已有原语**给东西（`Modifier` / `Counters` /
   `Scaling` / `Notify`），不需要改核心。这一版刻意把这条钩子留在明面上，
   而不是替内容先定一个数。

**这一版没有做的事**（同 §三的精神，逐条写清）：

- 没有改任何门槛、时长、倍率、层数——`git show --stat` 里没有一个数值。
- 没有给阶段发奖励（理由见上一条第 3、4 点）。
- 没有动 `BuildingView.NextMilestoneAt`（那是**单座建筑**的"再买 N 个"提示，不是层内阶段）。
- 没有把阶段铺到其余 10 个包上：末世 / 图书馆的解锁门用的是**历史累计**，
  §11.2.6 那个判据对它们给不出结果，要另立规则；其余包等减层定了再切。
- 没有量"真人每层多久"（§4.8 那条边界仍然成立）。

**这一版新量出来的一个数**（`CONTENT_AUTHORING` §11.2.6 那张表）：
"一层里能买到几座新建筑"就是这一层的段数上界——公司 5 / 8 / 8、
实验室 5 / 7 / 8×5、九命 6 / 8 / 9×7、神明与文明 5 / 7 / 8 / 9 / 9、
赛博 5 / 7 / 9 / 9 / 9、梦境 5 / 9 / 9 / 9 / 9（实测 2026-10-03）。
它是"上界"而不是"该取的值"：9 段意味着几乎每买一座建筑就进一段。
