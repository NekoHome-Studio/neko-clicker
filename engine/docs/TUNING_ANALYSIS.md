# ⑥ 的两件事：难度跨度与套件墙钟（数据与选项）

> 状态：**只做了测量与选项分析，没有动任何东西。**
> 这一节的存在理由：这两件事都属于"调优"，收益最不确定，所以先把**已测到的数**摆出来，
> 让决定基于数而不是感觉。凡是我没有实测的，我都标了"未测"。

## 一、难度跨度：1.4 ~ 11.8 游戏小时（8.4 倍）

数字来自 `PrestigeTests.EraPacks_PermanentUpgradesAreAffordableWithinOneRun` 每次运行打印的
实测行（机器人跑到结局，不是估计）：

| 包 | 到结局的游戏小时 | 层数 |
|---|---|---|
| #4 文明 | 1.4 | 5 个时代 |
| #10 公司 | 1.9 | 3 轮重组 |
| #6 末世 | 3.0 | 5 次重启 |
| #5 赛博 | 5.3 | 5 层 |
| #3 实验室 | 5.9 | 7 批 |
| #8 梦境 | 6.0 | 5 层梦 |
| #7 神明 | 7.5 | 5 套神话 |
| #9 图书馆 | 11.1 | 5 本书 |
| #2 九命 | 11.8 | 9 层 |

**先把话说清楚：这不是"难度"的跨度，而是"内容量"的跨度。** 层数从 3 到 9，
每层各自的时长也不一样，两者相乘就是这 8.4 倍。所以"该不该收敛"取决于一个
**只有你能回答的问题**：你希望一局是多少小时？我能算，但"多久算合适"不是技术问题。

### 选项（按代价从低到高）

- **(a) 不动。** 8.4 倍的跨度本身就是内容差异的体现（九命 9 层 vs 公司 3 轮）。
  代价：玩家看到"这一局要 12 小时"时可能直接不开始。**零工作量。**
- **(b) 只收敛最长的那两个（图书馆 11.1 / 九命 11.8）**，把层内门槛压低。
  代价：要重跑包络测量（`--simulate` 到结局）并重设门槛，且**动的是已发布内容的平衡**，
  会影响老存档的进度观感。中工作量。
- **(c) 给所有包一个统一的"到结局时长目标"，逐个标定。** 代价最高，
  而且会抹掉"不同包规模不同"这个可能是刻意的差异。**我不推荐**，除非你确认要统一。

**我倾向 (a) 或 (b)，而 (a) 其实是更诚实的默认**——因为没有任何证据表明
8.4 倍是错的；它只是"不一样"。要动它，先要有一个目标值。

## 二、套件墙钟：并行之后瓶颈变成了一条用例

实测（`tools/build.ps1 --timing` 与 `--timing --serial`）：

| | 串行 | 并行（16 核） |
|---|---|---|
| 全套墙钟 | 261.1s | **149.7s** |
| `PrestigeTests.EraPacks_...` 单条 | 98.5s | **143.9s** |
| 其余 430 条合计 | ~163s | —— |

**关键发现**：并行把这个套件从 261s 压到 150s，但**最慢那条自己被 CPU 竞争拖慢了**
（98.5 → 143.9s），于是**整个套件的墙钟现在由它一条决定**。再加线程没有用——
瓶颈已经从"CPU 总吞吐"变成"单条最贵的用例"。

那条用例在做什么：把 **9 个包各跑一局到结局**（就是上表那些小时数的来源）。

### 三个杠杆与它们的真实代价

| 杠杆 | 预计 | 代价 / 风险 | 对玩家有好处吗 |
|---|---|---|---|
| **② 让每个固定步更便宜** | **未测** | 低（改的是 `ProductionCalculator` / `ModifierResolver` 这类纯计算） | **有**——真玩时的帧率也吃这条 |
| **① 跨用例共享"跑一局"** | 261 → 约 180s（估） | 中：要统一"什么叫一次自然游玩"，而那会**改变多个守卫重放的轨迹与打印的数字**；这类改动最容易变成"数字变了，但不知道是内容坏了还是机器人换了" | 没有 |
| ③ 再加并发度 | **0** | —— | 没有（已被单条瓶颈限制） |

**我建议先做 ②，而且第一步是"测"不是"改"**：套件里 11 个包总共要快进三千多游戏小时，
成本 = 模拟秒数 × 30Hz × 每步成本。**每步成本目前只是一个从两个数据点推出来的估计
（约 23 µs）**，没有单独测过。测法：用 `--timing` 对比同一份内容在"只推时间"与
"推时间+买卖"两种机器人下的逐条耗时，把每步成本与外围开销（`BuyGreedily` 每次建
整份 `Snapshot`）分开。**分开之后才知道该优化哪一边**——否则很可能花大力气优化了
占小头的那半边。

**①要谨慎**：它的收益（省 80s 左右）不如它的风险大。它属于"动守卫重放内容"的改动，
而这个仓库今天已经因此栽过一次（粗步长让探针量的是步长而不是内容）。
