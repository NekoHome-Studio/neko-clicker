## 0. 写死的约束（任何创意先过这五关）

1. **零第三方依赖**（含测试框架）；MSBuild `-m:1`、无 NuGet 网络。
2. **公开 API 只增不改**——动 `NekoClicker.Core` 公开表面 = minor + 重生成 `PublicApi.txt`；不动 = patch 或不升版。
3. **存档格式不动**（`SaveSerializer.CurrentVersion` 仍为 `1`）。要加存档状态的必须先过 D5，标 ⚠️。
4. **引擎/内容分离**：优先"内容包自己能做"（`IGameModule` / `Counters` / `Modifier` 有先例）。
5. **主线长度不变（本版新增，硬约束）**——任何候选都**不许**让"从第一层走到结局"变长。判据（全部满足才算过）：
   - **不加门槛**：不往任何 `EraDefinition.Completion` / 结局条件 / 解锁链上添新的必做项；
   - **不加必答**：不新增会拦结局的待答表态（1.6.0 起"答不完拿不到结局"，多一条表态 = 主线变长）；
   - **不占主循环**：入口可选、可无视，不往点击/购买的主循环里塞新的必看弹窗；
   - **不稀释密度**：同屏信息量与作答节奏不因它变慢（纸条那种"收起就走"的形态才是合格线）。
   - 例外只有一种：**全新内容包自带的主线**（A4）——它自己定义自己的长度，不碰既有 11 包的主线。
   - **这条是守卫，不是散文**——`engine/tests/EraStageTests.cs` 加 `MainLineLengthTests`，横扫 `TestGame.AllContentPacks()`（派生式，新包自动进网，照 `AllEraPacks` 的先例），四条断言：
     1. **冻结长度**：每包的 `{纪元数, 最大 Index, 每个 EraDefinition.Completion.Describe() 指纹}` 必须与**用例内写死的期望表**逐字相同 ⇒ **加纪元 / 抬门槛 / 换指标 = 红**。期望表不入本文档——真相只留一份，免得文档与用例各说各话。
     2. **不加必答**：`ChoiceDefinition` **没有**"是否拦结局"字段（已核实）——拦结局的机制在 `EndingDefinition.Condition`，所以此条 = 冻结 `{EndingDefinition.Id, Priority, Condition.Describe()}` 指纹，与第 1 条同表同判。表态目前**只能**经 `IGameMetrics.StanceWeight(string)` 进条件树（`NumericMetric` 里没有表态指标），新增任何引用表态的条件叶子即红，且需同步过第 1 条。
     3. **三个盯死点**：`capsule_*` / `second_life_*` / `stages_walked_total` 不得出现在任何条件树里；树源 = 建筑/升级/成就的 `Unlock` + `EraDefinition.Completion` + `EndingDefinition.Condition`（四类消费者全覆盖）。`NumericMetric` 里**没有**阶段数与徽章指标，所以这条只能是条件树扫描，**不能**写成指标白名单。末尾 `Check.AtLeast(纪元总数, 40, …)` 防空扫。
     4. **堵后门**：`CustomCondition` 的谓词不可指纹（`Describe` 只是作者自己写的 `Description`），是唯一能绕过第 1 条悄悄加门槛的叶子——所以完成条件/结局条件里**不许**出现 `CustomCondition`。现状是内容里零使用（守卫首跑即绿）。
   - 现状基线（本版实测）：11 包中 9 包有纪元、共 **49 个**（九命 9、实验室 7、公司 3、其余各 5；`Neko`/`Cafe` 零纪元）；`Stages` 目前只有公司用。**白名单守卫（`GameContentBuilder.MonotonicMetrics` / `ForbiddenInCompletion`）只管"指标会不会下降"，不管"门槛有没有被抬高"——上面第 1 条补的正是它漏的那半。**

**前置**：1.13.1 已打包并自检通过（RELEASING ⑨ 已走；⑩⑪ 打 tag / 推送 / 看 CI 仍待人工放行，`1.11.0`~`1.13.1` 都只活在 `main` 上）；创意默认排在发布动作之后，除非明确并行。

## 诊断：旧池子为什么显得空（v3 新增）

> 这一节回答用户的原话："现在的创意库里面几乎没有有价值的东西。"诊断成立，根因有三：
>
> 1. **11 个包其实是同一个循环换 11 张皮**——点击 → 建筑 → 纪元链 → 结局。引擎真正的差异化接缝
>    （`IGameModule` / `Choice` / 衰减 / 继承）每个只被用过一次、当点缀。"换包即换游戏"这句主张，
>    目前只兑现了"换皮"，没兑现"换游戏"。
> 2. **档 A/B 里 90% 是"把已有的东西显示出来"**（纪念卡 / 时间线 / 徽章）**或文本彩蛋**（跨包门牌）。
>    没有一条改变**怎么玩**、**包与包之间**、或**引擎作为开源产品**的价值。
> 3. **第五关（主线长度不变）被当成了挡箭牌**——它其实该读成"新价值必须活在门槛结构**之外**"。
>    而那正是有趣的设计空间：可选系统、元层、玩家表达、异步社交、内容创作。
>
> v3 据此补三个档：**档 C 改变怎么玩**、**档 D 引擎作为产品**、**档 E 跨包元层**。每条仍过五关，
> 主线影响逐条审计（见 §3）。
>
> **顺手修掉的过期事实**（池子自己也会腐烂，这正是 §0 说的"文档不该跟提交赛跑"的反面教材）：
> - **A2 说"seed 只在终端"——错**。`GameHost` 两个宿主都收 `seed`（`GameHost.cs:112`），引擎本就是
>   `DeterministicRandom`、RNG 状态已进存档（`State.RandomState0/1`）。A2 缺的只是 URL 门。
> - **A6 的环还在用 `ninelives`**——D16 已拍板统一成 `ninelines`（1.13.1），这条彩蛋现在解锁了。
> - **§0 前置"1.12.1 仍未打包"**——已过期，现在 1.13.1 已打包自检（⑩⑪ 未走）。
> - **一个被想重了的约束**：`SaveData.Counters` 是 `Dictionary<string,double>`，**加新计数器键 ≠ 改存档格式**。
>   所以"可花第二资源""叙述者"这类**不过 D5**——旧池子默认把它们当成了动存档，凭空抬高了门槛。

## 档 C — 改变"怎么玩"（让"换包即换游戏"成真）

> 这一档每条都在回答同一个问题：**引擎能不能承载一个不是 Cookie Clicker 的游戏？**
> 目前 11 包都是"点击 → 建筑 → 纪元"。下面三条各换掉一个核心假设。全过五关；
> C1/C2 是新包（第五关唯一例外：自己的主线自己定），C3 是可复用接缝。

### C1 — 《猫娘电台》：点击是干扰的包 · 代价 M · ✅ 已落地（2026-11-13）

**论点**：第一个**主动点击反而有害**的包。你是电台编排者，"点击"是一个你可以**选择无视**的听众来电；
核心循环是**排班 / 编排**（随 tick 生长的节目单），不是点击。手痒去点，会**打断正在播的节目**
（掉一段收听率）。这把增量游戏的核心动词从"点"反转成"忍住别点、把节目排好"。

- **为什么有价值**：它是"换包即换游戏"的第一份**实物证据**——不是换皮，是换循环。引擎侧零改动：
  `ClickBasePower` 压到极小、`IGameModule` 驱动节目单、金猫改成"听众来电"（可接可不接）。
  A4 的"电台编排"概念卡由此从主题升级成**机制论点**。
- **主线影响：零（对既有 11 包）**——新包自己的主线只用单调指标（累计播出时长）；"打断"只影响一个
  **会掉的**收听率，而会掉的量**不进完成条件**（R3，照图书馆先例）。
- **拆步骤**：① 1 层 MVP（一个节目单模块 + 3 档节目）；② 数值配方沿用已验证曲线；③ 模块离线补算是硬要求；
  ④ 先 1 层再铺满；⑤ 不升版（内容包）。
- **风险**：反转核心动词可能让玩家前 5 分钟困惑——入门纸条（1.11.0 先例）必须在第一次"打断"时教会"别点"。
  这是叙事教机制的正当用武之地。

> **落地纪要（2026-11-13）**：第 12 个内容包 `engine/content/Radio`，引擎零改动——反转靠
> `BroadcastModule` 订阅 `ClickedEvent`（每点一次收听率掉 0.5%）＋ `ClickBasePower=0.1` 的数值配方。
> 收听率走 `Scaling(CustomCounter)`，均衡 L*=240×播音建筑数；会掉的量不进完成条件（R3）。
> **对"1 层 MVP"的偏离**：转生结算要求 `Era < MaxEraIndex`，一层包永远舍不了命、执照恒为 0，
> 永久线结构性买不起——故做**两层**（band_1 → band_2），给一次真实舍命结算。
> **验收**：619/619（含新增 RadioContentTests 三条）＋ api-test 123/123 ＋ web-smoke 342/342；

## 档 D — 引擎作为产品（开源引擎的真正价值）

> 用户原话："这个引擎不要动它，就作为一个开源引擎项目。"这一档不碰 `engine/core` 的玩法，
> 而是让**引擎本身**更值钱——可复现、可标定、可创作、可分享。全是工具链 / 宿主侧，零核心改动。

### D1 — 回放带：seed + 命令流 = 完整回放 · 代价 M · 推荐首做（引擎侧）· 确定性守卫已落地（2026-11-13）

**进展（2026-11-13）**：**"确定性守卫 + 回放演示"那一半已落地**——`ReplayTests` 三条（同 seed 同命令逐字节相同 /
异 seed 分叉 / 录命令流回放逐字节相同），见 `OPEN_WORK` §0.53 与 `CHANGELOG` `[未发布]`。
**留白**：宿主侧命令流记录 + 回放文件格式（独立信封）是下一半，也撑起 A2 / E2。原论点保留如下。

**论点**：引擎是命令驱动的（`Click` / `BuyBuilding` / …），且**本就确定性**（`DeterministicRandom`，
RNG 状态已进存档）。那么 **seed + 命令流 = 一整局的完整回放**。这是引擎能给出的**最强 bug 报告格式**
（"这是我的种子和命令日志，复现我的 bug"），也是挑战 / 速通验证的地基。

- **为什么有价值**：它把"确定性"从一句主张变成一个**可守卫的性质**——同 seed + 同命令序列 ⇒ 快照逐字节相同。
  这条性质一旦有测试守着，回放、挑战、bug 复现全都站得住。
- **主线影响：零**——回放是**独立产物**（像导出信封），不动存档格式、不占主循环。
- **拆步骤**：① 命令流记录（宿主侧，带序号 + 模拟时间戳）；② 回放器（喂 seed + 命令流，重放）；
  ③ **确定性守卫测试**（同 seed 同命令 ⇒ 快照逐字节一致）；④ 回放文件格式 = 独立信封，不进 `SaveData`；
  ⑤ 不升版（宿主 / 工具）。
- **风险**：命令流必须含**所有**影响状态的输入（含表态作答、金猫点击），漏一个就回放分叉——
  守卫测试要横扫真实命令集。
