# 终局判定的"作答宽限"：方案与取舍

> 状态：**待决策**。本文只定规则，不含实现。
> 触发这次讨论的 defect 见 `docs/ROADMAP.md` 阶段 3C-1 与 `tests/.../LabEndingTests.cs`。

---

## 1. 问题

结局一旦条件成立就**立刻锁死**（`EndingSystem` 一次性语义）。而末层的表态机会
与末层主线完成可能落在**同一个检查周期**里。实测（探针，`--panel` 无关，纯模拟）：

| 机器人步长 | 乌托邦权重 | 待答 | 落定的结局 |
|---|---|---|---|
| 30s | **6**（三次表态全答上） | 0 | **end_open**（兜底） |
| 5s | **6** | 0 | **end_open** |
| 1s | **6** | 0 | **end_open** |
| 0.25s | **6** | 0 | **end_utopia**（承诺的那条） |

粗步长下玩家**答对了全部三次表态，却仍然拿到兜底结局**——因为结局在他说出口之前就落定了。

## 2. 为什么"改检查顺序"解决不了

现有顺序是 `CheckEnding() → CheckAchievements() → CheckLore() → CheckChoices()`。
把它改成 `CheckChoices()` 在前**没有用**：

```
第 N 拍：钱同时跨过"末层表态门槛"与"末层完成门槛"
拍内  ：CheckChoices 让表态进入待答复队列（只是触发，没有人作答）
拍内  ：CheckEnding 看到完成 → 兜底落定 → 永久锁死
拍后  ：玩家作答 → 权重变成 5 —— 已经晚了
```

**玩家的作答永远发生在触发它的那一拍之外。** 人的反应时间不可能塞进一个检查周期。
同理"同一拍判两次结局"也只对自动作答的机器人有效，对人不成立。

结论：缺的不是执行顺序，而是**"条件成立之后、落定之前"的一段等待**。

## 3. 要定的三条规则

### 规则 1：宽限期怎么计量？

| 选项 | 好处 | 代价 |
|---|---|---|
| **(a) 模拟秒（推荐）** | 与存档语义一致（离线也算时间流逝）；实现最简；不需要玩家学新操作 | 挂机三天回来会发现结局已自己落定 |
| (b) 真实秒（wall clock） | 最贴合"给人反应时间"的直觉 | 存档要记 wall clock；改系统时间可作弊 |
| (c) 不超时，必须玩家主动点"放弃" | 完全由玩家掌控 | 把"回避表态"从"什么都不做"变成"必须做一次操作"，与验收 ③ 的初衷相悖 |

**推荐 (a)，宽限期 30 模拟秒。** 理由：这个框架的既有语义是"世界在你不看的时候也在前进"
（离线收益、离线期间的计数器增长都按这个来），所以结局的宽限也走模拟时间，
是**同一套世界观**，而不是新学一条规则。

### 规则 2：跨会话（退出再进来）怎么算？

计时存在 `GameState` 里、随存档走，退出期间继续流逝。

- **若离线期间宽限期已过**：回来时会发现结局已经落定 —— 与"离线收益照算"一致。
- 需要一次明确的验证：离线 3 小时后进游戏，结局落定的时机是否符合预期。

### 规则 3：兜底结局的地位？

**推荐：超时视作放弃，兜底照常到达。** 不改验收 ③。

兜底结局存在的意义就是"回避表态也有收场"。如果加了"必须主动放弃"，那回避本身就
变成了一次操作，兜底也就失去了它要守的那类玩家。

## 4. 推荐方案的实现清单

**语义**：结局条件成立后进入"已就绪"；就绪期间若还有未答复的表态，**暂不落定**；
等玩家答完，或距就绪已过宽限期，再落定。落定后仍然永久停止（一次性语义不变）。

**状态**：`GameState` 新增一个时间戳 `EndingReadyAtPlayTime`（`0` = 尚未就绪）。
——**不需要按表态逐条计时**，一个"条件首次成立的时间"就够。

```
if (EndingsReached.Count > 0) return null;
if (EndingReadyAtPlayTime == 0) {
    if (没有任何结局条件成立) return null;
    EndingReadyAtPlayTime = PlayTimeSeconds;          // 记住"够条件了"
}
bool pending = PendingChoices.Count > 0;
bool graceOver = PlayTimeSeconds - EndingReadyAtPlayTime >= GraceSeconds;
if (pending && !graceOver) return null;               // 给玩家留出作答时间
…照旧按 Priority 挑一个落定…
```

**存档**：`SaveData` 加一个 `double EndingReadyAtPlayTime`，**不升版本号**
（R8：新字段有安全默认值）。

**UI 义务**：就绪而暂不落定的这段时间必须**看得见**（例如状态栏"结局已就绪，
还有 N 项未答复"）。否则玩家不知道自己正处于决定命运的窗口里——那就只是把
"被抢走"换成了"不知道自己被给了机会"。

**测试**：
1. **顺序敏感（红→绿）**：造"末层完成与末次表态同拍"的最小场景，
   断言承诺的那条结局胜出。这是本文存在的理由，必须能证明它现在是红的。
2. **超时**：挂着不答 → 宽限期过后落到兜底。
3. **不回归**：既有 406 条（11 个内容包）全绿。

## 5. 明确不做

- **不改检查顺序** —— 第 2 节已说明它解决不了玩家延迟。改了还要解释"为什么依赖结局的成就晚一拍"。
- **不加"放弃"按钮** —— 见规则 1(c)。
- **不为每条表态单独计时** —— 一个时间戳够，多余的状态是多余的可疑点。

## 6. 已知的不确定

- **30 秒是拍的，不是量的。** 应该实测一次"从表态触发到玩家作答"的真实间隔（人类）。
  太短则手慢的玩家仍被抢，太长则末层的收尾被拖得没感觉。
- 这份方案会给模拟循环加一处新状态，而它**与离线时长耦合**——需要一次专门的验证
  （挂机跨越宽限期边界时，落定时机是否符合预期）。
